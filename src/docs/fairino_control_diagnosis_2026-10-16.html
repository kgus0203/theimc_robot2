1. 문제와 증상

MoveIt은 계획과 실행을 성공 처리하는 경우가 많았지만, 반복 운전 중 실제 로봇의 관절 피드백이 ROS 명령을 점점 늦게 따라가다가 다음 오류로 궤적이 중단됐다.

State tolerances failed for joint 4
Position Error: -0.200028, Position Tolerance: 0.200000
PATH_TOLERANCE_VIOLATED
... 0.743초 후 ...
ServoJ rejected (SDK code 14), robot alarm main=0, sub=0

오류 당시 WebApp과 직접 조회한 로봇 알람은 모두 0/0이었다. 따라서 SDK code 14는 로봇 자체 알람이 최초 원인이 아니라, ROS가 궤적을 중단한 이후 ServoJ 명령이 거절된 후속 현상이었다.

연결 초기화 과정에서 함께 발견한 문제

  • 연결 직후 실시간 상태 구조체의 오래된 alarm=1/23 값을 검사해 정상 로봇을 오류로 판단했다.
  • 수동 모드 또는 비활성 컨트롤러 상태에서는 계획만 성공하고 실제 로봇이 움직이지 않을 수 있었다.
  • ServoMoveStart() 호출 순서와 현재 위치를 명령 위치로 동기화하는 과정이 필요했다.
  • 관절 명령 유효성 검사 범위가 J6까지 포함되지 않는 코드가 있었다.

2. 진단 방법과 원인 확정

오른쪽 경로를 반복하면서 /fairino5_controller/controller_state와 /arm/joint_states를 rosbag으로 기록했다. 동시에 ServoJ RPC 호출 시간과 100 Hz 제어주기를 계측했다.

수정 전 같은 첫 번째 경로의 시작 후 12초 시점에서 J5 오차가 회차마다 약 0.052 rad씩 증가했다.

당시 ServoJ 호출 자체는 대부분 3~5 ms였고 네트워크 오류나 로봇 알람은 없었다. 하지만 controller_manager는 100 Hz, 즉 10 ms 주기로 실행되는 반면 ServoJ의 명령 전송 주기 cmdT도 정확히 0.010초였다. 통신과 스케줄러 오버헤드를 흡수할 여유가 없어 로봇 내부 명령 큐가 반복마다 조금씩 밀린 것이 선형 오차 증가의 원인이었다.

확정 원인: 속도 자체나 순간 RPC 지연이 아니라, 100 Hz 호스트 주기와 동일하게 설정한 ServoJ cmdT=0.010으로 인한 명령 큐 누적.

3. 적용한 해결 방법

  1. 연결 직후 현재 관절 위치를 읽어 state와 command를 동일하게 초기화했다.
  2. ResetAllError() 후 1초 대기하고 GetRobotErrorCode()의 최신 main/sub 값을 직접 검사했다.
  3. RobotEnable(1) 후 상태를 확인하고, 수동 모드이면 Mode(0)으로 자동 전환했다.
  4. StopMotion → ServoMoveEnd → ServoMoveStart 순서로 Servo 모드를 초기화했다.
  5. 비활성화 시 ServoMoveEnd → StopMotion → CloseRPC 순서로 종료하도록 했다.
  6. J1~J6 전체의 유효성을 검사하도록 범위를 수정했다.
  7. ServoJ 전송 주기를 0.010에서 0.008초로 변경했다.
  8. read, ServoJ RPC, controller period의 최대 시간을 1,000주기마다 출력하고 10 ms 초과를 별도 경고하도록 했다.
// 100 Hz host period보다 작게 두어 전송/스케줄러 여유 확보
const int code = _ptr_robot->ServoJ(
    &command, &external,
    servo_acceleration, servo_velocity,
    0.008F, 0, 0);

주요 구현: frcobot_ros2/fairino_hardware_v3_9_5/src/fairino_hardware_interface.cpp

5. 속도 최적화 시험

오른쪽 상단 3개 좌표만 사용하고, 각 설정을 5회 반복했다. 가속도는 0.03, path tolerance는 0.2 rad, ServoJ cmdT는 0.008초로 유지했다. 각 회차는 3개 좌표 이동 후 대기 자세로 복귀했다.

7. 남은 관찰 사항

  • 실시간 스케줄링: 현재 시스템의 ulimit -r=0 때문에 controller_manager가 FIFO RT 우선순위를 적용하지 못한다. 이번 장애의 직접 원인은 아니었고 cmdT 0.008이 관찰된 10~15 ms 수준의 간헐적 주기 변동을 흡수했다.
  • MoveIt 종료 오류: Ctrl+C 종료 시 class-loader 객체 해제 순서로 move_group -11이 발생한다. 실제 궤적 실행과 ros2_control 하드웨어 종료는 정상이며 별도의 종료 처리 문제다.
  • 시험 범위: 속도 비교는 오른쪽 상단 3개 좌표 기준이다. 전체 9개 좌표 및 좌우 전환 운전에서는 운영값 0.12 / 0.03으로 추가 장시간 시험을 권장한다.
판정: 간헐적 궤적 중단의 원인은 해소됐다. 반복 오차 누적이 사라졌고, 0.15 / 0.03까지 실패 없이 통과했다. 현재 운용 균형점은 0.12 / 0.03이다.
